# DBA audit — Nexus PostgreSQL

**Run:** 2026-09-25  
**Role:** DBA  
**Database:** `nexus`, PostgreSQL 17.11, connected read-only as `pguser`  
**Scope:** live catalog, data-integrity and projection checks; current SQL migrations; continuity against the retained 2026-07-22 and 2026-08-22 audits.

## Method and limits

This was a read-only live audit. It inspected all non-system schemas (33 schemas and 593 relations), trigger bindings, the Conduit replay comparator, selected audit/evidence write surfaces, password enforcement, lease expiry, and notification attachment. Source review included the current `sql/V190`–`V202` migrations and the CI bootstrap catalog.

Nexus managed-service and UI status commands reported every listed unit inactive or unknown. That prevents an end-to-end service-health assertion. PostgreSQL itself was reachable, had 87 visible sessions, and eight visible sessions whose current query included `LISTEN`; therefore the database evidence does **not** establish a present `pg_notify` subscriber outage.

The normal Nebula audit-record API, Assembly, timeclock, procedure registry, and TTS service were unavailable at boot. After elevated localhost access was available, the audit receipt was recorded in Nebula as inspection `dee4fddc-a0cb-4942-88e2-4c9eb2bd8350`. TTS was still unavailable.

## CRITICAL

### C1. Conduit’s current-state projection disagrees with its own event replay for every projected work request

**Promise:** `conduit.work_request_events` is the append-only event ledger and `conduit.work_request_state` is its current-state projection. `conduit.check_projection_drift(uuid)` is the non-destructive proof of that promise.

**Actually true:** all 26 rows in `conduit.work_request_state` return `has_drift = true` from the live comparator. The live event ledger contains **zero** rows, whereas every state row has a non-NULL `last_event_id`. The state, vision-stage, and IR-version fields agree with the comparator defaults; all 26 failures are the `expected_last_event_id` (`NULL`) versus `live_last_event_id` mismatch.

**How verified:**

- `SELECT count(*) FROM conduit.work_request_events;` returned `0`; `work_request_state` returned `26` rows.
- The catalog contains the comparator and three Conduit triggers, so this is not the July audit’s missing-trigger/missing-function condition.
- `SELECT ... FROM conduit.work_request_state CROSS JOIN LATERAL conduit.check_projection_drift(work_request_id) WHERE has_drift` returned all 26 rows.
- The live function replays only `conduit.work_request_events` and uses `IS DISTINCT FROM` for `last_event_id`, making this mismatch intentional detection rather than a NULL-comparison false positive.

**Blast radius:** any consumer treating the Conduit state table as replayable, event-derived state cannot prove lineage or reconstruct its state from the designated ledger. The data may look operationally plausible, but the database’s authoritative consistency test says it is not replay-consistent.

**Required action:** decide whether the event rows were intentionally archived, moved to another canonical store, or lost. If they were moved, change the comparator and the documented source of truth together. If not, restore/backfill the event history from a verified source and run the comparator as a release/operational gate. Do not silence or weaken the comparator without replacing the proof it supplies.

## GAP

### G1. Resolution claim-evidence links and admission receipts remain rewriteable audit facts

**Promise:** the Resolution-side claim/evidence and admission tables are described as durable evidence and assessment history.

**Actually true:** the live catalog has no immutability trigger on either `resolution.execution_claim_evidence` or `resolution.execution_admission_receipt`. `pguser` has both `UPDATE` and `DELETE` privilege on both tables. The link table has useful FK and vocabulary checks, but those do not prevent a confirmed link from being rewritten or removed; the admission table has FKs and a primary key only.

**How verified:** live `pg_trigger`, `pg_constraint`, and `has_table_privilege` queries. This is a live confirmation of the 2026-08-22 static G2/G3 finding, not merely source inference.

**Required action:** make the policy explicit. If these rows are audit facts, use insert-only enforcement (with an explicit, narrow supersession/expiry path if required) and restrict direct mutation. If they are mutable workflow records, change the durability/append-only claims and define a history surface that is actually immutable.

## DRIFT

No data-vocabulary drift was demonstrated in this pass. The broad trigger-returning-function scan did find 81 unattached functions, concentrated in `nebula` and `vision`; many have names consistent with retired view-trigger surfaces. The scan is a lead, not a finding: view `INSTEAD OF` triggers and historical migration functions must be classified against their current view/base-table surface before any function is reported as missing enforcement.

## OBSERVATIONS

### O1. Password enforcement is live and clean on both declared surfaces

`assembly.users` (34 rows) and `gateway.users` (2 rows) each have a `NOT NULL password`, a validated bcrypt-or-empty `users_password_bcrypt_check`, and the attached `trg_bcrypt_write_guard`. There are zero empty and zero non-bcrypt passwords under the policy `password LIKE '$2%' AND length(password) = 60`. This verifies the V202 enforcement path currently holds.

### O2. Two previously reported guard issues are now demonstrably improved

- `nebula.notify_open_question_event()` contains `OLD.status IS DISTINCT FROM 'RESOLVED'`, fixing the NULL-sensitive comparison reported in July.
- `execution.receipts` now has both `trg_receipt_governance` and `trg_receipts_immutable`; the prior audit’s assertion that receipts lacked immutability is no longer current.

### O3. Lease expiry currently has no active overdue rows

`tackle.role_leases` contains 1 `ACTIVE`, 47 `EXPIRED`, and 256 `RELEASED` rows; no active row has `expires_at < now()`. `execution.leases` likewise has zero active expired rows. This is a point-in-time data check, not proof that sweeper scheduling will remain healthy.

### O4. Two non-product-looking schemas remain in the primary database

`dbg2_080885d2` (9 relations) and `probe141_f83c25b8` (3 relations) are present alongside product schemas. Their purpose and retention policy were not discoverable from catalog names alone. This is not called corruption, but the database inventory should document whether they are durable test/probe artifacts and who owns expiry/cleanup.
